# Active Work Board

Use this file as the live source of truth for active Codex-agent work. The Senior Fullstack Lead / Orchestrator owns updates to this board unless a work packet explicitly assigns a section to another role.

## Board Rules

- Update this board when a work item changes state, owner, operating mode, priority, blocker status, or GitHub check-in status.
- No implementation starts until the item has a product brief, architecture contract, QA plan, Orchestrator work packet, WIP clearance, assigned lane, one directly responsible developer, reserved write scope, and state `Ready for Implementation`.
- Each lane developer may have only one `In Implementation` or rejected `Needs Revision` item.
- Rejected items stay on the same row and move to `Needs Revision`; the Orchestrator assigns the revision to an available qualified developer with a non-conflicting write scope. Prefer the original developer only when free.
- Product Owner priority changes must update the affected row before downstream agents continue.
- Released items must include GitHub check-in evidence.
- Orchestrator must run status sweeps during active execution: reconcile worker state, board state, dirty files, reserved scopes, and gate dependencies; stale or silent workers must be prompted for handoff, continued unblocked work, or blocker report.
- After a valid handoff to QA, a developer may pull the next Orchestrator-assigned implementation task. If QA rejects the prior item, an available qualified developer picks up the revision; no developer may own two active implementation/revision tasks at once.
- Developer handoff to `Ready for QA` requires developer-run focused tests/build/UI smoke/API checks/live-data validation as applicable. Missing validation must be recorded as a concrete blocker before QA starts.
- QA capacity may scale when multiple items wait for verification. Assign one QA worker per item/evidence file, avoid parallel checks that compete for browser/database/ports, and keep final signoff traceable to one QA owner.
- Laptop resource gate: before starting new local servers, builds, tests, Playwright/browser runs, Docker services, or new Codex worker agents, check memory utilization. Do not start new process-heavy work at or above 95%; after the gate closes, wait until memory drops below 90% before starting more.
