## Common Verification Rules

- Market scope must remain explicit: `region=IN`, `assetType=STOCK`.
- Language must remain research-support only. Reject direct transaction wording such as buy now, sell now, guaranteed, place order, execute order, live trade, or financial advice.
- Provider-heavy, full-universe, scheduler, and large repair actions must be stubbed in automated tests and verified manually only through bounded/dry-run paths unless the PO and Architect explicitly approve a heavier live-data pass.
- Batch actions must show scope, batch size or cap, progress metadata, partial-failure behavior, and next action.
- Empty, partial, stale, and blocked states must be first-class acceptance scenarios, not incidental error states.

## Brief 1 - Trusted Review Universe Readiness And Repair Path

### Acceptance Scenarios

- `FULL_REVIEW`: scoped `IN / STOCK` readiness summary shows trusted universe count, required data-through, stored data-through, blocker counts at acceptable thresholds, and Today Review can display the same mode without contradiction.
- `LIMITED_REVIEW`: summary explains the trusted subset is usable, identifies excluded counts by blocker category, and tells the user whether to proceed with limited review or repair data first.
- `NO_REVIEW`: summary explains that Today Review cannot publish candidates, shows top blocker categories and affected counts, and points to the next safest repair action.
- Repair path: top blocker maps to one bounded action, dry-run or small-batch by default, with explicit user action required before provider-heavy or full-universe work.
- Failure/partial states: failed provider diagnosis, manual metadata required, stale price, missing history, and retry-blocked rows are shown as repairable or manual blockers without hiding Today Review impact.
- Contract reconciled: Market Data Foundation owns the canonical scoped readiness summary, using `FULL_REVIEW`, `LIMITED_REVIEW`, `NO_REVIEW`, `trustStatus`, `userDecision`, readiness counts, blocker categories, and bounded request metadata from the architecture contract.

### Backend Test Targets

- Extend or add targets near `backend/tests/modules/market-data-foundation/market-data.service.test.ts` for readiness mode calculation, blocker ranking, next safe action, bounded dry-run behavior, and no implicit full-universe execution.
- Extend `backend/tests/modules/data-quality-engine/data-quality-engine.service.test.ts` for data-quality readiness contributions to the scoped summary.
- Extend `backend/tests/modules/today-trade-review/today-trade-review.service.test.ts` for consuming the same readiness state, including `FULL_REVIEW`, `LIMITED_REVIEW`, `NO_REVIEW`, stale data-through, unavailable membership, and partial membership scan behavior.
- Add/adjust route contract tests once Architect defines endpoint ownership and response shape.

### Frontend/UI Smoke Targets

- Market Data/Data Quality page renders a single scoped readiness summary for `IN / STOCK`, top blockers, counts, and next action.
- Today Review displays the same readiness mode and dates as Market Data/Data Quality.
- UI differentiates wait, repair data, and proceed with limited review.
- Repair controls are visibly bounded, and dry-run/small-batch progress is shown.
- Existing anchors: Market Data UI already checks universe health, signoff, trusted review universe, operational repair run, and repair workflow; Today Review UI already checks `LIMITED_REVIEW`, `NO_REVIEW`, partial scans, and research-only wording.

### Manual/Live-Data Checks

- With local backend/frontend running, validate current `IN / STOCK` readiness summary against Today Review latest run.
- Capture a dry-run repair plan and confirm no provider-heavy work starts.
- If a bounded repair action is manually run, record before/after blocker counts, batch cap, and next action.

### Evidence To Collect

- Backend command output and passed test names.
- UI smoke command output and screenshot of readiness summary plus Today Review matching state.
- API response sample for scoped readiness and Today Review latest/run state.
- Live-data notes: current mode, top blockers, counts, data-through dates, repair action offered.

### Heavy/Provider Actions To Avoid Or Stub

- Stub provider validation, price backfill, business metadata fetch, catalog identity repair, and scheduler execution in automated tests.
- Do not run full catalog/universe repair as part of QA signoff.

### Regression Risk

- High. This touches data trust gates, Today Review eligibility, repair operations, and shared readiness language.

### QA Signoff Or Reject

- Sign off only if Market Data/Data Quality and Today Review agree on mode, counts, blocker meaning, and next action for the same scope.
- Reject if repair actions can trigger unbounded provider work, if `NO_REVIEW` still promotes candidates, if `LIMITED_REVIEW` hides exclusions, or if modules show contradictory readiness labels.

## Brief 3 - Calibration Readiness And Confidence Guardrails

### Acceptance Scenarios

- Calibration page shows selected horizon, usable sample count, sufficiency threshold, and confidence tier.
- Low or zero sample sufficiency labels calibrated outputs as limited and explains whether raw score, calibrated score, or no score should be treated as authoritative.
- Downstream influence is suppressed or downgraded when sufficiency is too low.
- Batch calibration remains scoped and bounded.
- Strategy Decision and Today Review consume calibration readiness without overstating confidence.
- Contract reconciled: Calibration readiness must expose `calibrationEvidence`, `calibrationReadiness`, `downstreamInfluence`, and `authoritativeScore`; missing persisted evidence must fail conservative rather than imply confidence.

### Backend Test Targets

- Extend `backend/tests/modules/signal-calibration-engine/signal-calibration-engine.service.test.ts` for zero samples, low samples, enough samples, confidence tiering, authoritative score selection, and scoped batch calibration.
- Extend route/validation tests for horizon, batch, and scope bounds.
- Add integration-adjacent service tests in Today Review and Strategy Decision once readiness consumption contracts exist.

### Frontend/UI Smoke Targets

- Calibration page shows sample sufficiency, selected horizon, confidence tier, raw vs calibrated evidence columns, and low-sample warning.
- Batch run payload includes `IN / STOCK`, selected horizon, and capped batch size.
- Downstream pages show limited/suppressed calibration influence without presenting calibrated score as upgraded evidence.
- Existing anchors: Signal Calibration UI already checks low-sample warning, raw/calibrated/evidence columns, scoped batch payload, and bounded batch size.

### Manual/Live-Data Checks

- Validate current local calibration state for `IN / STOCK` and selected horizon.
- Confirm any zero-sample or low-sample page does not visually rank calibrated scores as stronger than raw scores.
- Spot-check Today Review/Strategy Decision language when calibration readiness is limited.

### Evidence To Collect

- Backend test output for sufficiency tiers and downstream suppression.
- UI smoke output and screenshot of low/zero sample guardrail.
- API response sample with confidence tier and authoritative-score signal.
- Manual notes from downstream pages.

### Heavy/Provider Actions To Avoid Or Stub

- Stub signal outcome samples and calibration batches.
- Do not run broad recalibration over the whole signal table in automated QA.

### Regression Risk

- High. Calibration can appear mathematically authoritative even when evidence is absent.

### QA Signoff Or Reject

- Sign off only if low sufficiency clearly downgrades or suppresses calibration in both source and consuming modules.
- Reject if calibrated scores are displayed as authoritative with insufficient samples, if downstream modules omit readiness, or if batch calibration is unbounded.

## Brief 4 - Cross-Module Actionability Consistency

### Acceptance Scenarios

- Shared actionability state separates market environment, data readiness, signal evidence, strategy proof, and trade-plan readiness.
- Research Hub does not state or imply actionable setups are allowed when Today Review or Trade Plans are blocked.
- Today Review, Research Hub, Strategy Decision, and Trade Plans use consistent labels: `Ready`, `Limited`, `Blocked`, `Unproven`, and `Insufficient Data` or Architect-approved equivalents.
- User sees the next best research action when actionability is limited or blocked.
- Research-support language is preserved across every module.
- Contract reconciled: Research Hub owns the normalized actionability object and shared vocabulary; hard data, Today Review, or Trade Plan blockers must reduce overall actionability before softer signal/calibration states.

### Backend Test Targets

- Extend `backend/tests/modules/research-hub/research-hub.service.test.ts` for actionability-state aggregation, blocked upstream gates, and no live-trading readiness labels.
- Extend `backend/tests/modules/today-trade-review/today-trade-review.service.test.ts` for shared label mapping and blocked/limited promotion rules.
- Extend `backend/tests/modules/strategy-decision-engine/strategy-decision-engine.service.test.ts` and repository tests for strategy proof/readiness mapping.
- Extend `backend/tests/modules/trade-plan-risk-engine/trade-plan-risk-engine.service.test.ts` for paper-readiness and blocker funnel contribution to actionability.
- Add a small cross-module contract test if Architect creates a shared mapper/service.

### Frontend/UI Smoke Targets

- Research Hub, Today Review, Strategy Decision, and Trade Plans display consistent labels for the same mocked backend state.
- Research Hub distinguishes healthy market environment from actionable review readiness.
- Next best research action appears when blocked or limited.
- No prohibited transaction language appears in page body.
- Existing anchors: Research Hub UI checks proof-driven triage and research-only language; Today Review UI checks grouped states and research-only wording; Strategy Decision UI checks readiness columns; Trade Plans UI checks funnel diagnostics and blocker empty state.

### Manual/Live-Data Checks

- Run the app locally and compare Research Hub, Today Review, Strategy Decision, and Trade Plans for the current `IN / STOCK` state.

### Evidence To Collect

- Backend test output for aggregation/label mapping.
- UI smoke output and screenshots from all four modules.
- Manual comparison table: module, market state, data state, signal evidence, strategy proof, trade-plan readiness, next action.
- Text scan or assertion evidence for research-only language.

### Heavy/Provider Actions To Avoid Or Stub

- Stub all module responses for cross-module UI smoke.
- Do not run real strategy evaluation, Today Review generation, or trade-plan generation solely to create consistency states unless explicitly approved and bounded.

### Regression Risk

- Very high. This is a cross-module contract and wording change that can create unsafe user interpretation if one module lags.

### QA Signoff Or Reject

- Sign off only if all four modules use the same actionability precedence for the same data state and avoid transaction guidance.
- Reject if any module claims readiness/actionability while a hard upstream gate is blocked, or if market health is conflated with trade-plan readiness.

## Brief 5 - Trade Plan Paper-Readiness Proof Chain

### Acceptance Scenarios

- Trade Plans shows a prioritized blocker funnel with counts by data quality, strategy proof, backtest evidence, risk geometry, and scope.
- Each blocker category points to the module or action that can resolve it.
- Detail pages show canonical hard blockers and suppress positive readiness reasons while hard blockers are active.
- Batch generation is scoped to `IN / STOCK`, bounded, and reports progress, generated count, skipped count, failures, paper-ready count, proof timeframe, and top blockers.
- Today Review consumes paper-readiness without treating blocked plans as actionable candidates.
- Contract reconciled: Trade Plan Risk Engine owns `paperReadinessProofChain`, canonical blocker categories, persisted `paperReadyOnly` filtering, and hard-blocker precedence; Today Review must consume blocked readiness conservatively.

### Backend Test Targets

- Extend `backend/tests/trade-plan-risk-engine.paper-readiness.test.ts` for canonical hard blockers, positive-readiness suppression, and proof chain reasons.
- Extend `backend/tests/modules/trade-plan-risk-engine/trade-plan-risk-engine.service.test.ts` for funnel diagnostics, exact counts, batch discovery, failure details, paper-readiness diagnostics, and scoped proof timeframe.
- Extend repository tests for persisted readiness filters, stale geometry repair, scope/proof filtering, and legacy inclusion only when explicit.
- Extend Today Review service tests for blocked paper-readiness candidates remaining blocked or watch-only.
- Add backtesting integration target once Architect defines the backtest evidence contract.

### Frontend/UI Smoke Targets

- Trade Plans page shows blocker funnel counts and module/action pointers.
- Empty state explains why no scoped plans are paper-ready.
- Batch generation sends scoped bounded request and renders progress summary.
- Detail view shows hard geometry/proof/data blockers and does not show positive readiness reasons beside active hard blockers.
- Today Review does not promote blocked trade plans as actionable.
- Existing anchors: Trade Plans UI already checks funnel diagnostics, bounded batch generation, detail no-plan state, currency formatting, and geometry blocker suppression of readiness reasons.

### Manual/Live-Data Checks

- With current local data, record the no-paper-ready state and top blocker funnel.
- Open at least one blocked plan detail, if present, and verify hard blockers plus absence of contradictory positive reasons.
- Compare Today Review candidates with Trade Plans readiness so blocked plans are not treated as actionable.

### Evidence To Collect

- Backend test output for paper-readiness classification and funnel diagnostics.
- UI smoke output and screenshots of funnel, empty state, batch progress, and blocked detail.
- API response sample for funnel diagnostics and a blocked plan detail.
- Manual notes linking each top blocker to a resolving module/action.

### Heavy/Provider Actions To Avoid Or Stub

- Stub candidate discovery, strategy decisions, backtest summaries, and plan generation in automated tests.
- Do not run broad batch generation or real backtests unless bounded and approved as a manual check.

### Regression Risk

- High. This affects user interpretation of plan readiness, Today Review promotion, and proof-chain transparency.

### QA Signoff Or Reject

- Sign off only if no-paper-ready states are explanatory, blocker counts are prioritized, detail pages avoid contradictory reasons, and Today Review respects blocked paper-readiness.
- Reject if hard blockers coexist with positive readiness claims, if batch generation is unbounded, or if blocked plans become actionable candidates.

## Remaining QA Risks And Follow-Ups

- Brief 1 risk: readiness counts can drift if implementation counts attempts or stale repair rows instead of distinct current stocks; live-data evidence must compare Market Data/Data Quality output with Today Review's consumed snapshot.
- Brief 2 risk: trading-row maturity and missing-price diagnostics can be conflated; QA must verify `notYetMatureSignals`, `missingPriceHistoryCount`, and `insufficientFuturePriceCount` remain separate per horizon.
- Brief 3 risk: existing calibration rows without evidence may look confident unless handled conservatively; QA must include a missing-evidence/legacy-row case if persistence fields are added.
- Brief 4 risk: Research Hub overview fanout and partial child failures can produce optimistic actionability; QA must verify partial failures downgrade to `LIMITED` or `INSUFFICIENT_DATA`, not `READY`.
- Brief 5 risk: list/detail/funnel paths can disagree after read-time canonical repair; QA must verify the same scoped blocked plans stay blocked across funnel, candidates, detail, Today Review, and Research Hub.
- Live-data signoff may still be limited by local dataset state. If current data cannot naturally produce a required state, QA should use backend fixtures/mocks for automated evidence and record manual live-data limitations.
